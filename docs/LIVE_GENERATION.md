# Live sprite generation

How the asset loop (brief → generator → render → verifier → fix → best-of) runs as a server route, with model-written `build(k)` code executed only where it can reach nothing: in QuickJS compiled to WebAssembly (in a worker thread on the server, in a Web Worker in the player's browser) or in a sandbox. The route exists (see "The route"), and the game draws each creature in the player's browser from its code (see "The code in the browser"); the comparison, timings and probes below are the measurements it was designed from. Three sandboxes and Mubit were measured on 24 Oct 2026, timed from a client in the UK: [Shotcup](https://shotcup.dev) (a Scale-plan account, `pipeline/render-shotcup.ts`; the numbers were taken with its Python predecessor), [Vercel Sandbox](https://vercel.com/docs/vercel-sandbox) (the team's Pro plan, `pipeline/render-vercel-sandbox.ts`) and [boat.dev](https://boat.dev) (the 7-day free trial, `pipeline/render-boat.ts`). Unless a section says otherwise, the render timings used the kit before its speed-ups (sha256 `cf66f505c9e9…`, 212,457 bytes); the kit on `main` now (sha256 `335b0f4040a7…`, 225,487 bytes) renders the same pixels 4.8-9.3x faster on Shotcup (see "Kit speed-ups"). Mubit was measured with generator calls only; the full generate → render → verify → fix round trip was run later, through the route (see "What was run live").

**Recommendation: render live candidates in Vercel Sandbox, one fresh microVM per candidate.** It is fast, measured under load and the simplest to operate: the render goes from 10-107 s on Shotcup (old kit) to about 1.4-2.4 s until the PNG is in hand (from the UK to `iad1`; a route running in `iad1` saves part of the round trips), so the model calls, not the render, set the latency of a candidate. Best-of-N and many sprites at once can run in parallel (below). The isolation boundary is a VM per candidate with egress denied by a policy set from outside the VM through the API; it does not depend on the banned-identifier tripwire (`pipeline/build-code.ts`) or on what a JavaScript runtime chooses to expose. On Vercel the route authenticates with its own OIDC token (documented; not tried from a deployment), so no sandbox key is added to the deployment.

**boat.dev is the second renderer, and the cheapest at volume.** It renders faster and costs about $0.00001 a candidate against Vercel's $0.0008, which doesn't decide anything here (model calls take longer, and 1,000 sprites cost $1.60 on Vercel). The differences that remain favour Vercel: on boat the network lock-down, the non-root account and the cron/`at` denial are ours, inside a VM whose default account is root, rather than a policy set from outside the VM; a fresh sandbox per candidate runs into start limits, and reusing one sandbox avoids them only by making a Linux account the boundary between candidates; the deployment would need a `boat_` key; and boat's machines are in the EU while the functions run in `iad1`. Keep `render-boat.ts` for volume and as a second vendor. **Shotcup is the fallback that needs no VM**, limited by about three concurrent runs.

How to run Vercel Sandbox: `networkPolicy: "deny-all"`, `persistent: false`, 1 vCPU, a session `timeout` of 2 minutes and a `runCommand` `timeoutMs` per render (the renderer uses 30 s), one VM per candidate so that a build cannot leave anything for the next one, and `stop()` after the PNG is read (it took 1.2-1.3 s; a route can return the PNG first). Snapshots made creation slower than uploading the 216 KB of kit and runner, so the renderer uploads them each time.

Grouping guidance:
- **One candidate per sandbox run.** On Shotcup a batch shares one module scope, so one build can overwrite another's PNG; on Vercel and boat each candidate gets its own VM (or its own account). Never batch candidates in one Shotcup run.
- **Send all generator calls at once.** Mubit's limits are far above any batch of sprites we would send, and a batch takes as long as its slowest call.
- **Render each candidate in its own sandbox as soon as its code arrives**, as a pipeline rather than batched stages, with up to about 25 Vercel Sandbox renders at once (4.2 s for 25 against 13.4 s for 50). Verifier and fix calls follow per sprite, and the engine's own flags still skip the verifier.
- **Spread boat.dev candidates across a reused sandbox** if the start limits matter; a fresh sandbox per candidate takes one start each, and the trial allows 25 an hour.
- Not yet measured: the whole loop at concurrency (generator, render, verifier and fix together). `pipeline/run.ts` runs 4 briefs at once by default for local and Vercel Sandbox, 2 for boat.dev and 1 for Shotcup (`--concurrency N`); the Vercel figure is a conservative default, not the measured ceiling.

## Mubit

Generator calls use exactly the request `pipeline/run.ts` sends: `generator.md` as the system prompt, `Brief: …` as the user message, `max_tokens` 1500, `metadata.user_id`, no `temperature`, model `claude-opus-5-5`. They were run at 1, 2, 3 and 6 concurrent, 24 calls in all; every output was rendered by the local renderer.
- All 24 returned 200 with no retries, and all 24 builds rendered. Two cyclops outputs were flagged `clipped_at_edge`, which is the normal verify-and-fix case.
- Batch wall time for the 6 briefs: 16.5 s at 1 concurrent, 8.4 s at 2, 8.1 s at 3, 6.8 s at 6.
- Per-call latency doesn't change with concurrency. The median is about 2.1 s (1.75-2.7 s) for 53-113 output tokens. The cyclops brief is the outlier at 5.2-8.0 s for 400-620 tokens. So a batch takes as long as its slowest call.
- Input is about 5.4k tokens per call (the `generator.md` system prompt).
- Mubit passes Anthropic's rate-limit headers through: 1,000 requests/min, 2,000,000 input tokens/min, 400,000 output tokens/min. The probe used at most 6 requests, 8k input and 1k output tokens of that. At about 5.4k input tokens per generator call the input limit allows about 370 generator calls per minute. Mubit is not the bottleneck; the sandbox renderer is.

### Prompt caching

Repeat calls resend the same 5.4k tokens, so `pipeline/mubit.ts` marks each system prompt as the end of a cacheable prefix (`cache_control: {"type": "ephemeral"}`, 5 minute TTL; `claude-opus-5-5` caches prefixes of at least 512 tokens and bills a read at 0.05x the input price, a write at 1.25x). The first measurement was made with the cache off (`cache_read_input_tokens` was 0 on all 24 calls). Checked live afterwards with two generator calls in a row, one system prompt: the first wrote 5,379 tokens to the cache (2,347 ms, 17 uncached input tokens, 60 output tokens), the second read all 5,379 back (2,090 ms, 17 uncached input tokens, 122 output tokens, `cache_creation_input_tokens` 0). So Mubit passes `cache_control` through. The two latencies can't be compared directly (the outputs differ in length). Calls that start together all miss, because an entry exists only once the first response has begun; later calls hit. `--no-prompt-caching` turns it off.

## Where the model's code runs

The owner's decision: "It shouldn't render it into an image; we only have code and run the code that comes back." A creature is delivered as the build code the model wrote, and the player's browser runs that code to draw it. One render still happens on the server, only so the verifier model can judge pixels. The AGENTS.md hard rule allows model-generated build code to run in exactly these places, and in no other:

| Where                                               | What it is                                                                                                                                                   | Used for                                                                                  |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| QuickJS compiled to WebAssembly, in a worker thread | `pipeline/render-quickjs.ts` + `quickjs-worker-thread.ts`: a thread per render, no host functions, limits inside, the thread terminated at an outer deadline | the job's judge render (default, `CREATURE_RENDERER=quickjs`)                             |
| QuickJS compiled to WebAssembly, in a Web Worker    | `src/scene/creature-worker.ts`: the same core (`pipeline/quickjs-core.ts`), the same prepared kit, a worker per creature that the page terminates            | drawing the creature in the player's browser                                              |
| A sandbox                                           | Vercel Sandbox (a microVM, no network) or Shotcup; boat.dev for experiments                                                                                  | the job's judge render with `CREATURE_RENDERER=sandbox`; `bun run assets -- --render ...` |
| The local renderer with an allowlisted environment  | `pipeline/render-local.ts`: a bun subprocess that sees only `PATH`, `HOME`, `TMPDIR`, `LANG` and `KIT_OUT`                                                   | the offline pipeline on a developer's machine                                             |

Never `eval` it, pass it to `new Function`, `node:vm` or `import()`, or run it directly in the app, a route, the page or a worker's own scope. Why not: `node:vm` failed 8 of the 16 isolation probes (below, "In-process rendering"), and the function that starts a job holds `MUBIT_API_KEY`. QuickJS has no host functions at all: the host evaluates scripts and reads one size-checked object back, and a WebAssembly module can touch only its own linear memory. What that does not give is protection from a bug in QuickJS or Emscripten that the probes did not find (nothing fuzzed the engine) and timing side channels.

Before the owner's decision the route ran model code only in a Vercel Sandbox (a microVM with no network) because the function holds the keys; on Shotcup the code runs in a fresh GocciaScript engine per run with a virtual filesystem. The probes below found nothing of ours for it to reach in either. The sandbox renderer stays, selected with `CREATURE_RENDERER=sandbox`, as the fallback.

## The route

Built: each night the sea can send a new creature, made live through Mubit, judged from a render in QuickJS (or a Vercel Sandbox), and kept in a gallery as its build code; every player's browser draws it from that code. The routes are `src/app/api/creatures/` (Node.js runtime, Zod at every boundary, short error strings only), their logic is `src/server/creatures/`, the loop is `pipeline/loop.ts`, and the contract with the game (the `Creature` record, archetype-derived stats, request and response shapes) is `src/game/creature.ts`.

| Route                               | What                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/creatures/next` `{seen}` | The newest gallery creature not in `seen` (`{kind:"ready", creature}`). If there is none: the running job when one is running (`{kind:"generating", jobId}`, so many players share one generation); else a new job when the limits allow; else `{kind:"none", reason:"rate-limited", retryAfterSeconds}`, or `reason:"unavailable"` when generation is not configured or storage fails. |
| `GET /api/creatures/jobs/:jobId`    | The job as `CreatureJob`: `step` (queued, writing, drawing, rendering, judging, fixing, done, failed), the `creature` when done, a short `error` when failed. A job whose status has not moved for longer than `maxDuration` reads as failed (`timed out`).                                                                                                                             |
| `GET /api/creatures/:id/code`       | The creature's build code as `text/plain`, `cache-control: public, max-age=31536000, immutable`, `x-content-type-options: nosniff` and `content-security-policy: default-src 'none'; sandbox`. The browser checks its SHA-256 against the record's `build.codeSha256` before it runs it. 404 for an unknown id, 503 when storage fails (never cached).                                  |
| `GET /api/creatures/:id/sprite.png` | The PNG from the private Blob store, same cache header. Only for creatures drawn before the code was delivered (their record has no `build`); the job no longer writes a PNG, so a new creature answers 404.                                                                                                                                                                            |

### The job

```
POST /api/creatures/next  ── no unseen creature, nothing running, limits allow ──►  claim the global slot, answer {generating, jobId}
  └─ after()                                                    (the same invocation keeps running after the response)
     1. writing    brief writer: one Mubit call, prompts/creature.md → {name, lore, sprite brief, archetype, 4 modifiers in {-1,0,1}}
                   validated with the contract's Zod schema; given the gallery's names (and the three built-in monsters) to avoid repeats;
                   a random thread of myth is offered as inspiration, because Mubit takes no temperature and the same prompt gets the same creature;
                   every brief aims at one body plan the kit draws well (satyr, cyclops, minotaur, harpy, winged or plain humanoid, centaur, hydra) with at most two named parts
     2. drawing    three candidates at once (CREATURE_CANDIDATES): one generator call each (prompts/generator.md) from the same brief,
                   each with a different nudge, because Mubit takes no temperature → build(k) source, text only
     3. rendering  per candidate, as soon as it is drawn: tripwire (build-code.ts), then QuickJS in a worker thread of its own (default), or with
                   CREATURE_RENDERER=sandbox a Vercel Sandbox of its own, booted from the pinned snapshot, deny-all network
     4.            engine flags (clipped / too small / too big / too short) → score 0, no verifier call
     5. judging    verifier (Mubit, sees the 4x PNG) on each survivor, in parallel; borderline scores are taken twice
     6. fixing     only if the best candidate is not already accepted: one fix turn on that candidate alone, then 3-5 again; best-of
     7. accept     a verifier pass, or a score of at least 6 with no engine flags (the bar, calibrated below). Anything else: the job fails and stores nothing
                   anchorY from the render's bbox (lowest row + 1 - 4 px of shadow, over 128); stats are derived by creatureStats(), never taken from the model
                   store creatures/sprites/<id>.ts (the code; no PNG), then creatures/records/<id>.json with build.codeSha256 and
                   build.pixelsSha256 (the pixels the verifier judged), then the job: done
```

Model code only ever reaches a renderer (QuickJS with no host functions, or a sandbox): the function holds `MUBIT_API_KEY`, so it never evals, transpiles or imports what the model wrote (`pipeline/build-code.ts` is a tripwire in front of the renderer, not the boundary). Every Mubit call goes to `https://api.mubit.ai/anthropic/v1/messages` with `claude-opus-5-5`, never sends `temperature`, and marks the system prompt cacheable. The job reports to Blob at every step; a failure ends as one of a few fixed strings, and no model output, stack trace or error message is stored, returned or logged (the log has job ids, steps, Mubit request ids, status, timings, token counts and the verifier's scores).

### How it survives function limits (`after()`, not Vercel Workflow)

`POST /api/creatures/next` starts the job with `after()` from `next/server` and declares `export const maxDuration = 300`. Under Fluid Compute (the default) a function runs 300 s by default on every plan and up to 800 s on Pro (documented limits, read 24 Oct 2026; not exercised on a deployment), and `after()` runs for "the platform's default or configured max duration of your route" (Next's `after` docs). A job took 28-78 s locally (below), 59 s on a preview deployment, so 300 s covers it with room for one slow Mubit call; the job itself gives up after 270 s (`JOB_BUDGET_SECONDS`) so it can record `failed: timed out` before the platform kills the invocation, and a job whose status has not moved for longer than `maxDuration` is read as failed by everything that looks at it (the job route, and the slot check that lets the next job start).

Why not Vercel Workflow: Workflow's gain is durability, surviving a crash or deploy mid-job and running past the function limit, and this job needs neither. It is short against the limit, a lost job costs one failed nightly attempt and a retry (the slot frees itself after `maxDuration`), and every step already writes its status to Blob, so nothing is hidden state. Workflow would add a dependency, its own step and replay semantics and a second place the job's state lives, for a failure mode that is cheap here. If jobs ever need to outlive 300-800 s (several fix turns, more candidates), move the loop's stages into workflow steps; `runLoop`'s `onStage` and the store are the seams.

### Storage and the one-job-at-a-time slot

All in the existing private Blob store (`BLOB_READ_WRITE_TOKEN`), under `creatures/` (`CREATURE_BLOB_PREFIX`; live tests used `creatures-dev/`):

| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `records/<id>.json`, `sprites/<id>.ts`, `sprites/<id>.png`             | The accepted creature and its build code (plain JavaScript, whatever the extension says); the PNG only for creatures from before the code was delivered. Ids start with their creation time (base 36), so a sort is newest-first; the record is written last, so a creature is in the gallery only when complete. |
| `jobs/<jobId>.json`                                                    | Job status, rewritten at every step. Claimed with a conditional write (create-if-absent, or `ifMatch` the version just read), so of several simultaneous starters exactly one wins; the rest follow its job.                                                                                                    |

### Rate limits

Only starting a job is limited; reading the gallery, and following a job that is already running, never is. Per visitor, 3 starts an hour (`CREATURE_MAX_STARTS_PER_VISITOR_PER_HOUR`); for the whole site, 40 a UTC day (`CREATURE_MAX_STARTS_PER_DAY`). A visitor is the HMAC-SHA256 of the first `x-forwarded-for` address under the secret `CREATURE_RATE_SALT` (at least 16 characters; without it generation is off); the address itself is never stored. Changing the salt resets everyone's count.

Races that remain, because the counts come from Blob listings and not from a transaction:
- The slot is atomic, and a job's marks are written before its job starts, so two jobs never overlap and a count is complete whenever a new job is considered. What can still slip through is a listing that lags a just-written mark (Blob listings are not documented as read-after-write consistent), letting one extra start through at the limit.
- A job that dies without finishing holds the slot until `maxDuration` has passed since its last step, so for up to 5 minutes nobody can start a new one (they follow the dead job and see it fail).
- Marks are never deleted, so a very old visitor key or day prefix is just a few tiny blobs; the daily and hourly windows ignore them.
- The same visitor behind many addresses (IPv6 privacy addresses, a mobile network) gets more starts; one address shared by many (an office) shares 3 an hour. The daily ceiling bounds the cost either way.

### The sandbox: a snapshot with Bun 1.4.4

Only with `CREATURE_RENDERER=sandbox`; the default renderer needs no snapshot.

The stock image (`vercel/sandbox/universal`, checked on 24 Oct 2026, Ubuntu 26.04.1, kernel 6.18.49) ships Bun 1.4.4 at `/usr/local/bin/bun`, which is also the latest release (`npm view bun version`). The render does not trust that to stay so: `bun run sandbox:snapshot` (`pipeline/sandbox-snapshot.ts`) boots a sandbox with a network allow-list of `github.com` and `*.githubusercontent.com` only, downloads Bun 1.4.4 from its GitHub release, checks the zip against the pinned SHA-256 (`bf8ccbfb…`, the release's `SHASUMS256.txt`), installs it at `/usr/local/bin/bun`, switches the policy to `deny-all`, checks `bun --version` is 1.4.4, copies in the kit and runner and a `SNAPSHOT.json` (kit sha256, bundle sha256, Bun version, the zip's digest), renders the committed `ex_lamp_lit.ts` and requires it to reproduce `public/sprites/lamp-lit.png` byte for byte, and snapshots with no expiry. It prints `VERCEL_SANDBOX_SNAPSHOT_ID=…`.

Render sandboxes boot from that snapshot with `networkPolicy: "deny-all"`, 1 vCPU, `persistent: false`, and run `/usr/local/bin/bun`. Before the first render with a snapshot, a process reads its `SNAPSHOT.json` once and refuses the snapshot, failing the render with a fixed message, when its bundle digest differs from the one computed from the `pipeline/kit/kit.ts`, `pipeline/render/*.ts` that are deployed, or when its Bun is not the pinned one. So a change to the kit or the runner needs a new snapshot and a new `VERCEL_SANDBOX_SNAPSHOT_ID` before it deploys, and the failure is loud, not a silently different sprite. The function reads those files and the prompts at runtime (`outputFileTracingIncludes` in `next.config.ts`); the kit and runner that render sprites are in the snapshot, not read for rendering. Sandbox auth in a deployed function is the platform's OIDC token; nothing from the function's environment is passed into the VM (the render command gets only `KIT_OUT`).

### Shotcup rules

Rules for Shotcup that follow from its measurements (the Vercel Sandbox settings are under the recommendation above):
- **One candidate per Shotcup run.** In a batch, every candidate's code shares one module scope: a probe build overwrote another candidate's `/out/victim.png` and pushed a forged stats row, and the run still succeeded. Batching also bought nothing (below).
- **Don't fan out.** The runtime had 4 workers. Runs beyond about three queued for 30 s and then failed (`failureKind: "daemon-error"`, "the runtime is busy; retry shortly"), and runs admitted together slowed each other down 1.6-3x (old kit). `render-shotcup.ts` retries the busy failure (up to 2 retries) instead of scoring it as broken code, and `pipeline/run.ts` runs one Shotcup brief at a time.
- **Set a render budget.** `timeoutMs` above the plan ceiling (Scale: 300 s) is clamped with a `timeout-clamped` warning. A timeout ends the run cleanly (`failureKind: "timeout"`). Pick a budget per sprite: with the current kit a temple needs about 12 s (107-111 s with the old kit), so a budget well under that would reject sprites the kit makes on purpose.
- **Never send `allowedHosts`** on render runs. Without it, `fetch` throws `PermissionDenied`.
- **Seed the drive at deploy time,** not per request. Writing the kit takes 0.43-0.65 s. An unchanged write makes no new version (`created: false`). Pinning the mount to that version id would stop a later kit write from changing a running job's renders. Not implemented or tested.
- **Keys.** `MUBIT_API_KEY` and the chosen renderer's key would become server-side environment variables of the deployment (today the README says the deployment has none and needs none: that changes with this route). Model output never runs where they live.
- **Artifact links are public capability URLs by default** (`artifactAccess: "public"`, kept for the plan's retention). The client reads `inlineBase64`, so the links aren't needed: send `retention: "none"` (tested, no speed effect) or `artifacts: "private"` (documented for MCP, not tried over REST).

## The code in the browser

What the server keeps, what the browser does with it, and what was measured, on 24 Oct 2026. The machine is the one the in-process measurements used (a Mac; Bun 1.4.3; the built app on `next start` with Node 26.8; Playwright 1.64.1). "iPhone" rows are WebKit with Playwright's `iPhone 14 landscape` device profile: Safari's engine on this Mac's CPU, not an iPhone, so a phone will be slower. Everything is over loopback, so no download time is in any number. Reproduce with `bun run build && bun run start -- -p 3730`, then `bun run check:creature-worker -- --url http://localhost:3730`.

### What is delivered

A creature's record has `build: { codeSha256, pixelsSha256 }` (`src/game/creature.ts`): the SHA-256 of the build code as `GET /api/creatures/:id/code` serves it, and of the 65,536 bytes of RGBA pixels the verifier judged (the PNG decoded; the job hashes what it judged, not a second render). The job stores the code (`sprites/<id>.ts`) and the record and no PNG. The recorded creature in a play carries `build` too, so a replay can draw it again. `GET /api/creatures/:id/sprite.png` stays for records without `build`.

The kit is part of what the pixels depend on. `bun run kit` writes `pipeline/prepared-kit.ts`, the kit as plain JavaScript (types stripped, `export` dropped, its names listed) with its SHA-256; `prepare-kit.test.ts` fails when the committed file is not what the generator writes from `kit.ts`. The server's worker thread and the browser's worker import that one file, so both draw with the same kit. A kit change moves the pixels of every earlier creature: their hashes no longer match and they would no longer come (see "Not verified").

### The worker

`src/scene/creature-render.ts` draws a creature when it is announced (a night with none loads nothing): it fetches the code, checks the code's SHA-256 against the record (a mismatch never reaches the worker), starts a Web Worker (`src/scene/creature-worker.ts`: QuickJS compiled to WebAssembly and the prepared kit), sends it the code and the limits, and checks the SHA-256 of the pixels that come back. The worker is terminated as soon as it answers or at the deadline, so a draw leaves nothing behind. Each creature is drawn once per page (`creaturePixels`, keyed by id and hashes) and shared: the night's texture (`shadowlessTexture` in `rim.ts`, which is what a loaded PNG goes through too: painted shadow removed, rim light, white flash, anchor) and the title panel's portrait both come from those pixels. In the worker the build runs as in the server's thread (`pipeline/quickjs-core.ts`): a fresh runtime and context, no host functions, no `Date`, a seeded `Math.random`, an allocator limit, a WebAssembly memory cap, a stack limit and an interrupt deadline. Any failure (a code fetch that fails, a hash that does not match, a worker error, the deadline) means no creature that night: it is not announced, the night starts without it, and it is not counted as met.

### Limits

Measured over the 58 committed sprites and hero frames with a throwaway script on Bun (`measure-inprocess.ts --floor` does the same for one sprite); the browser draws the 18 single sprites:

| Limit              | What real sprites need                                                                     | Set to                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| QuickJS allocator  | 512 KiB is the smallest limit that renders each; at most 1.03 MiB in use at the end of one | 8 MiB                                                                                                               |
| Stack              | 8 KiB or less                                                                              | 32 KiB. 64 KiB overflowed WebKit's worker stack before QuickJS's own check fired, so the limit has to stay under it |
| WebAssembly memory | stays at its initial 16 MiB                                                                | capped at 32 MiB (a typed-array bomb ends as `out of memory`)                                                       |

The stack finding matters beyond these numbers: the host overflowing first leaves the runtime half unwound, which the per-render worker contains (the worker reports a fixed failure and is terminated) but which is not the clean `stack overflow` the limit exists for.

### Headers

The page has no Content-Security-Policy, so the worker and the WebAssembly need no `worker-src` or `wasm-unsafe-eval`, and none was added: a policy that Pixi (which compiles shaders with `new Function`) and Next's inline bootstrap script would accept would not constrain the worker either. Checked on `next start`: the worker and its chunks are static assets (`/_next/static/chunks/*`, `cache-control: public, max-age=31536000, immutable`), the WebAssembly is `/_next/static/media/emscripten-module.<hash>.wasm` as `application/wasm`, immutable, gzip-encoded (503,134 bytes raw, 234,589 sent). The code route sends `content-type: text/plain; charset=utf-8`, `x-content-type-options: nosniff` and `content-security-policy: default-src 'none'; sandbox`, so a browser sent there shows text and runs nothing. Turbopack also emits the worker's TypeScript source as a static asset (`/_next/static/media/creature-worker.<hash>.ts`), which is public source anyway.

## Shotcup

### Why it is slow, and what helped

- **Why is Shotcup slow?** It runs the kit in GocciaScript, a bytecode interpreter with no JIT (`metrics.mode: "bytecode"`, about 14-25 M instructions/s), where bun compiles the same code to machine code. The kit's renderer is a ray marcher that evaluates signed-distance functions hundreds of thousands of times per sprite, and the old kit did that wastefully: every sprite rasterised at least twice (temple four times), the ground shadow took 60-89% of the time, and the shape functions allocated vectors and called `Math.max`/`Math.min`/`Math.abs`, which in GocciaScript cost about 0.4 µs each, four times a plain function call. Kit import (0.26 s) and Shotcup's own overhead (about 0.2-0.35 s per run) were never the problem.
- **What helped:** making the kit's renderer do less work, with identical pixels (PR #14): lamp-lit 10.2 → 1.76 s, house 24.9 → 3.83 s, satyr 21.9 → 4.55 s, temple 109.1 → 11.7 s on Shotcup. Locally in bun it is also 2.1-3.3x faster.
- **Can the kit go on a drive?** It already is (the `lampwarden` drive, mounted read-only at `/kit`). A drive mount and inline files measured the same (10.11-10.19 s vs 10.0-10.2 s for lamp-lit): the time was never in moving or loading the kit.
- **Can AOT help?** Only with the import, not the render. Shotcup can import a precompiled GocciaScript module (`import * as K from '/kit/kit.gbc'` from a drive works): kit import drops from 0.28 s to 0.02 s, the render runs the same bytecode at the same speed. That saves about 0.25 s per run: 13% for lamp-lit now (1.76 → 1.53 s), 0.2% for the old temple. It is undocumented on Shotcup and fragile (below), so the pipeline doesn't use it.

Client wall clock on Shotcup was 0.15-0.37 s above `engineMs`. All 18 committed sprites in one batch run took 107.8 s with the new kit (1 sample); six of them took 231-235 s with the old one. Local GocciaScript on the Mac is about 2.1-2.9x faster than Shotcup's runtime, so it is a useful free proxy for profiling.

What the changes did (local GocciaScript, 1 sample, ms: lamp-lit / house / satyr / temple, render + post): 4852 / 12346 / 9753 / 51300 before; the ground shadow was the largest cost (4015 / 4656 / 8517 / 32163 ms), because for every empty pixel in its bounding box it marched toward the light and, at every step, looped over every part, allocating two 3-element arrays for the bounding-sphere test. A GocciaScript micro-benchmark (1 M iterations each): a built-in `Math.max`/`Math.min`/`Math.abs`/`Math.sqrt` call costs 0.37-0.44 µs, a plain closure call 0.10 µs, allocating `[a, b, c]` 0.84 µs, ten arithmetic operations 0.16 µs. bun's JIT makes all of these nearly free, which is why the old kit was 100-300x slower on Shotcup than locally. The changes, in order of effect: cast the shadow once on the final pass and reuse the auto-scale probe as the first pass; skip parts and rays in the shadow march by bounding-sphere distance; visit the previous step's nearest part first; cache the nearest palette colour per distinct colour in `post()`; scalar shape distance functions instead of vector arrays; compute the surface normal once per pixel for the front part; refine depth only when a later part can matter; plain `larger`/`smaller`/`magnitude` functions instead of `Math.max`/`Math.min`/`Math.abs` (bit-identical, checked on 4.1 M argument pairs in bun and GocciaScript); a cheap bound for parts far from a pixel's light ray. After all of them: 632 / 1651 / 1916 / 5311 ms, and 605-613 / 1540-1562 / 1841-1886 / 4970-5045 ms for the final kit. Sorting each pixel's near shadow parts by bound was identical but no faster and was reverted; shifting the previous pass after an edge-fit move, culling union members by bounding box and a cheaper coverage-only probe were not tried, because they are not exact by construction. Cost: bun got slower on the `Math` replacement alone (lamp-lit render 15 → 17 ms, temple 77 → 85 ms), because bun inlines `Math.max`; overall bun is still 2.1-3.3x faster than before.

### AOT: a precompiled kit (.gbc)

GocciaScript can compile a module ahead of time to a `.gbc` bytecode file (`GocciaBundler`, [docs/bytecode-loading.md](https://github.com/frostney/GocciaScript/blob/main/docs/bytecode-loading.md), ADR 0153). Its own docs say what that saves: lexing, parsing and compiling, not execution.
- **Shotcup's engine:** the `Goccia` global in a run reports version `0.14.0-dev`, commit `e2c0118` (built 2026-10-22). That commit contains the precompiled-module loader (PR #1845, artifact format 96). Shotcup's docs don't mention `.gbc` at all.
- **Building it:** `GocciaBundler` built from `e2c0118` with fpc 3.2.2, run with the switches of Shotcup's default `strict` profile; the artifact records the profile and a mismatch is refused. `kit.gbc` is 1.25-1.31 MB (the source is 212-225 KB), over the 1 MiB limit for one file in a drive write, so it was written by a run that mounted a test drive read-write and joined two base64 chunks sent as run files (sha256 checked after the write).
- **It works:** `import * as K from '/kit/kit.gbc'` loads it, renders the same pixels (lamp-lit and house, 3 reps each, both kits) and runs the same number of instructions as the source kit.
- **Measured (3 reps, `engineMs`):** importing the kit alone: source 268-286 ms, `.gbc` 20-25 ms (old kit); source 275-282 ms, `.gbc` 22-24 ms (current kit). Full runs with the old kit: lamp-lit 10.14-10.48 s (source) vs 10.05-10.19 s (`.gbc`), house 24.78-24.91 vs 24.79-25.28 s: within noise. With the current kit: lamp-lit 1.75-1.78 vs 1.52-1.55 s, house 3.77-3.85 vs 3.53-3.62 s: the 0.25 s import saving is now 6-13% of a run.
- **Why it isn't used:** the artifact is tied to Shotcup's engine build. A Shotcup engine update that changes the format or profile would make every import fail (the loader raises an error instead of falling back to source), and Shotcup doesn't publish its engine version or document the feature. It also has to be rebuilt with a matching `GocciaBundler` on every kit change, and it can't be written to a drive with one ordinary write. If 0.25 s per run matters later, keep the source kit beside the `.gbc` and fall back on an import error.

### Starts, limits and cost

Limits, from `boat limits` and the [limits page](https://docs.boat.dev/limits.md): create, fork and resume each count as a start, in rolling windows; a refused start doesn't count. The trial allows 2 sandboxes at once and 5 starts a minute, 25 an hour and 75 a day; the $20 plan 100 at once and 12 / 60 / 200; the $100 plan 300 and 30 / 210 / 840. An organisation multiplies every limit and the included time by its seats (one plan price per seat). The sandboxes are cheap; the starts are the constraint, and only for a fresh sandbox per candidate:
- **The hourly limit stopped this evaluation.** After 25 fresh sandboxes in about 17 minutes, every create answered `429 rate_limited` ("25 sandbox starts per hour") until the window rolled. The reused-sandbox runs needed 2 starts for their 75 timed candidates and all the probes.
- **A fresh sandbox per candidate** needs one start per candidate. A sprite is one or two candidates (first try, one fix), so the trial allows 12-25 sprites an hour and 37-75 a day, the $20 plan 30-60 an hour and 100-200 a day, and a 5-seat $20 organisation ($100 a month) five times that. A best-of-N fan-out uses N starts at once against a 5 (trial) or 12 ($20) per-minute limit, and the trial runs only 2 sandboxes at once.
- **A reused sandbox** needs one start per sandbox lifetime. A warm `small` sandbox serves candidates back to back (0.4-1.0 s each) and several at once; on a paid plan its auto-stop can be up to 30 days or off (the trial caps it at 2 hours). One `small` sandbox on all month costs $0.018 × 730 h = $13.14, inside the $20 plan's included time.

Cost, from the [pricing page](https://docs.boat.dev/pricing.md) (per second while running, no fee per start, egress free; `small` $0.018/h, `default` $0.036/h) and the measured times: a fresh-sandbox candidate runs 1.1-3.5 s on `small`, about $0.000005-0.000018, so **about $0.00001 per candidate**, or about $0.02 for 1,000 sprites with one fix each (against about $1.60 on Vercel Sandbox), but those 2,000 starts are ten days of the $20 plan's start limit. A reused-sandbox candidate uses 0.4-1.0 s of running time, about $0.000003, but the sandbox bills while it waits. The usage API agreed with the rates: the warm `small` sandbox showed 271 s running as 135 balance seconds ($0.00135; `small` bills at half the `default` rate), the warm `default` one 42 s as $0.00042. The plan is the real cost: $20 a month at least, returned as compute time.

## In-process rendering

Question from the owner: can the build run directly in the process instead of in a sandbox, what does that cost in time, and how would it be isolated without side effects? This is a measurement and isolation spike, run on 24 Oct 2026. As a spike it changed nothing about live generation. It has since been adopted ("Where the model's code runs", "The code in the browser"): QuickJS in a worker thread is the `quickjs` renderer in `renderers.ts`, and the AGENTS.md rule allows it; `direct` and `node-vm` are still unselectable and still forbidden for model code. The rest of this section is the spike as it was measured, apart from the notes marked as done below.

Three renderers behind the `Renderer` contract (a fourth, on `isolated-vm`, was built and measured during the spike and left out of the pull request; see below), all in `pipeline/render-inprocess-*.ts` and all fed by the same prepared kit (`kit.ts` with its types and `export`s stripped: Bun's transpiler under Bun, `node:module`'s `stripTypeScriptTypes` under Node), so the modes differ only in where the code runs:

| mode          | file                          | what it is                                                                                                                                                                                                                                                                                                |
| ------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `direct`      | `render-inprocess-direct.ts`  | `new Function` in the host process. **Measurement only**: it refuses any script that is not byte-for-byte a committed `public/sprites/*.ts` or generated hero frame build, and it is not selectable.                                                                                                      |
| `node-vm`     | `render-inprocess-vm.ts`      | A fresh `node:vm` context per render. **Not a security boundary** (probes below); measurement only, and it refuses non-committed scripts unless the probe harness opts in inside a disposable child process.                                                                                              |
| `quickjs`     | `render-inprocess-quickjs.ts` | The kit and the build inside QuickJS compiled to WebAssembly (`quickjs-emscripten-core` 0.32.0 with `@jitl/quickjs-wasmfile-release-sync`, QuickJS 2025-09-13), a fresh runtime and context per render. The candidate.                                                                                    |
| `isolated-vm` | not in this pull request      | A V8 isolate per render (`isolated-vm` 7.0.1, native), plus a variant that starts each isolate from a heap snapshot holding the kit. How the QuickJS renderer works. `render/run_local.ts` uses the canvas shim only to write the PNG: the kit itself draws into a plain `Uint8Array` (`post()` returns `rgba`), so nothing canvas-like is needed inside the interpreter. Per render the host creates a runtime and a context (without the `Date` intrinsic), evaluates the prepared kit, then one script that wraps the build the way `run_local.ts` does (every kit export is a parameter of the build's wrapper function), runs `build(new Kit())` and `post(...)`, and evaluates to `{ stats, pixels }`. There are **no host functions at all**: the host reads the result object, checks that the pixel buffer is exactly 65,536 bytes and the stats string at most 4,096 characters before copying or parsing anything, validates the stats with the same Zod schema as every renderer, and encodes the PNG itself (the shim's encoder, so the bytes match under Bun). `Math.random` is replaced by a seeded generator (the kit never calls it); there is no clock, console, timer or module loader, and the host never runs promise jobs. Limits: an interrupt handler at a deadline (30 s by default), a 128 KiB stack limit, a 32 MiB QuickJS allocator limit and a 64 MiB hard cap on the module's WebAssembly memory. After a render that fails, the shared WebAssembly module is dropped and the next render loads a new one (about 11 ms), so a build that drove it out of memory cannot affect a later render. The stack limit and the WebAssembly cap came out of the probes: see "What the probes forced".

What the numbers say:
- **QuickJS is 1.6-10x faster than a Vercel Sandbox end to end** (0.25-0.7 s for the four small sprites and 1.9-2.4 s for temple, against 2.5-3.7 s), with no network round trip, no credentials and no VM to create. It is also by far the slowest in-process option: a bytecode interpreter running the kit is about 25-45x slower than the same kit under JavaScriptCore or V8 (temple 1.9 s against 44 ms direct), and 5-15x slower than the existing local subprocess (130 ms for temple), which is JIT-fast but not isolated. The time is the rasteriser, not setup: a runtime and context take 0.2-0.4 ms to create warm, evaluating the 201 KB prepared kit takes about 19 ms, loading the WebAssembly module about 11 ms once per process, disposing about 1 ms.
- A fresh WebAssembly module per render (no linear memory shared between renders) costs between nothing and about 0.15 s here; the difference is inside the noise. It is cheap enough to use if a shared module worries you.
- Cold is typically 20-100 ms above warm for QuickJS (the loaded Node run is noisier). The type strip of the kit is not in these numbers: 7 ms under Bun and 54 ms the first time under Node, which prints an ExperimentalWarning. A deployment should do it at build time and ship the prepared kit.
- `node-vm` is 2-4x slower than `direct`, because every access crosses the context boundary. `isolated-vm` is about as fast as `direct` plus 40-100 ms of isolate creation; a kit snapshot barely helps.
- The Vercel Sandbox rows are slower than the 1.4-2.4 s measured earlier from this client (2.5-3.7 s now). `runCommand` took 464-1115 ms inside the VM here, against the 69-391 ms the render itself takes, because that command also starts bun and transpiles the kit.

**Pixel identity.** All 58 committed sprites and hero frames render to exactly the committed pixels with `quickjs` under Bun and under Node 24, and with `direct` and `node-vm` under Node 24 (`bun pipeline/measure-inprocess.ts --identity --mode <mode>`); `isolated-vm` did too, on the spike. The kit has its own sine and arctangent and otherwise uses `sqrt`, `floor` and `imul`, which are exact in every engine, so QuickJS's maths does not differ. Under Bun the PNG bytes are identical to the committed files too. Under Node they differ in all 58, because Node's zlib compresses to different bytes; the decoded pixels are the contract.

**Memory and size.** QuickJS reports 0.8-1.0 MiB in use at the end of a render (temple 0.94 MiB), and the module's WebAssembly memory stays at its initial 16 MiB through repeated temple renders. Both limits can go down to those floors (`--floor`: an allocator limit of 1 MiB and a WebAssembly cap of 16 MiB still render temple and house); the defaults, 32 and 64 MiB, leave room for bigger sprites. Process RSS after the first sprite goes from 18 to 44 MB under Bun and from 93 to 148 MB under Node 24 (which includes the type strip); `direct` takes 18 -> 52-64 MB. What QuickJS adds to a function: the WebAssembly file (503 KB), about 80 KB of JavaScript (the two packages' entry files; 60 KB for the core's CommonJS build) and the 201 KB prepared kit, roughly 0.8 MB and no native binary. `bun build --minify` of the renderer and everything it imports, Zod included, is 148 KB. `isolated-vm` adds a native binary (0.77 MB for darwin-arm64) per platform and Node ABI.

**Where it runs.** `quickjs` passes the identity and probe runs under Bun 1.4.3 and Node 24.19.0, and a first pass also ran on Node 26.8.1. `isolated-vm` loads under Node 24 and 26 from its prebuilt binary and does **not** load under Bun (`dlopen` fails on V8 symbols JavaScriptCore does not have). Its README asks for `--no-node-snapshot` on Node 20+, which was not needed on 24.19, and its compatibility table lists 6.x for Node 24, while 7.0.1 (`engines` `>=24`) worked. The Node runs use a bundle made by `bun build --target node`, because the pipeline imports without file extensions, which Node cannot resolve. Nothing was deployed to a Vercel Function, only macOS arm64 was tested, and how Next.js traces the `.wasm` into a function (`outputFileTracingIncludes`) was not tried.

The pollution is real and the fresh context is what stops it.

### What the probes forced

Two of the first QuickJS runs failed, and both fixes are in the renderer:
- **`setMemoryLimit` does not bound typed arrays.** Four 32 MiB `Float64Array`s were allocated under a 64 MiB limit (QuickJS reported 134 MB in use and carried on), and the 1.5 GiB `memory` probe ran to the end with the host's RSS at 1.6 GiB. Objects, arrays and strings are counted (the 10M-object probe stops); `ArrayBuffer` backing stores are not. The fix is a hard cap on the module's WebAssembly linear memory (`new WebAssembly.Memory({ maximum })` passed through `newVariant({ wasmMemory })`): the allocation then fails inside QuickJS as an ordinary `out of memory` and the module stays usable. That memory is shared by every render of a module and never shrinks, so it sits at its high-water mark, at most the cap.
- **QuickJS's stack limit must be below the host's own call stack.** With `setMaxStackSize(1 MiB)`, and with no limit at all, a recursion made the host throw `RangeError: Maximum call stack size exceeded` from inside the WebAssembly call and left the runtime half unwound; on Node, disposing it then aborted the module (`Assertion failed: list_empty(&rt->gc_obj_list)`). The usable stack depends on the host: the largest safe values tried were 256 KiB on Node 24.19 (320 KiB failed) and 512 KiB on Bun 1.4.3 (768 KiB failed). The renderer uses 128 KiB (about 740 JavaScript frames), which renders all 58 committed sprites. A different host, or a deeper call chain into the renderer, could need less.

Also checked: `quickjs-ng` (`@jitl/quickjs-ng-wasmfile-release-sync` 0.32.0) is not faster here (lamp-lit 283-322 ms against 238-243 ms, temple 2.1-2.3 s against 1.8 s, same script, Bun), so the original QuickJS variant stays.

### Recommendation

**Is QuickJS in WebAssembly safe enough, and fast enough, to replace the sandbox for live renders? For this workload, yes, with conditions. `node:vm` and `direct` no. `isolated-vm` also contained the generic probes on current Node (with a host deadline and `dispose()`); QuickJS is preferred for the strength of its guarantee, for being a WebAssembly file instead of a native module, and for upstream maintenance, and `isolated-vm` is not in this pull request.**
- Safety. Nothing the build can name reaches the host: there are no host functions and no globals beyond the language's, and the host only reads a size-checked result object. The WebAssembly module can only touch its own linear memory, so a memory-safety bug in QuickJS's C code would corrupt that module and not the process (use a fresh module per render if that residual risk matters; it costs little here). All 16 probes, including the ones that broke `node:vm`, were contained on Bun and Node 24, and a render after a polluting one is pixel-identical. What this does not give: protection from a QuickJS or Emscripten bug the probes did not find (they exercise the JavaScript surface; nothing fuzzed the engine) and timing side channels (out of scope). The limits that hold it are three: the interrupt deadline, the WebAssembly cap and the stack limit, and the probes had to tune the last two.
- Speed. Against a Vercel Sandbox that takes 2.5-3.7 s from the UK, yes: 0.25-0.8 s for lamp-lit, house, satyr and a hero frame and about 2 s for temple, from a cold process. It is the slowest of the in-process options and it blocks its thread while it runs, so in a function it belongs in a `worker_thread` (or a small pool) and not on the request's event loop, with the interrupt deadline inside and a termination fallback outside. Whether the CPU time on a function costs less than the sandbox's VM creation and CPU time was not worked out.
- Compared with the sandboxes measured above, it is faster and simpler (no credentials, no cold VM, nothing to leave behind), and weaker in one way: the boundary is WebAssembly in the host's address space, not a hypervisor.

**Adopting it changed the hard rule in AGENTS.md, which was the owner's decision, and he took it.** The rule said model-generated build code runs only in a sandbox (Shotcup, Vercel Sandbox, boat.dev) or the local renderer with an allowlisted environment, and is never `eval`ed in the app or a server route. It now also allows QuickJS compiled to WebAssembly with no host functions, server-side in a worker thread or client-side in a Web Worker, and keeps forbidding `eval`, `new Function`, `node:vm`, `import()` and running the code directly.

What had to change to use it live (done in the pull request that adopted it; where it differs from the list, the note says how):
- **Rule and docs:** the AGENTS.md rule, `pipeline/README.md` and the "Why a sandbox and not the server" section above.
- **Code:** add `quickjs` to `RENDERER_NAMES` and `renderers.ts` with a default concurrency of 1 per worker, and keep `direct` and `node-vm` out. Prepare the kit at build time (strip the types once and ship the JavaScript) instead of at first use. Accept plain JavaScript build code, which is what the model writes, so the build-code type strip goes away. Run the interpreter in a worker thread with a termination fallback and an outer deadline above the interrupt deadline. Set the three limits from the largest real sprite plus margin. Make `next.config.ts` trace the `.wasm` file into the route. Keep `bannedIdentifierIn` as the cheap first filter.
- **Tests and CI:** run the QuickJS rows of `probe-inprocess.ts` and a pixel-identity check for the QuickJS renderer in CI. `pipeline/render-inprocess.test.ts` already pins the pixel identity, the deadline, the WebAssembly memory cap, the unreachable host, the refusal of unsafe names and the clean render after a polluting build.
- **Dependencies:** `quickjs-emscripten-core` and `@jitl/quickjs-wasmfile-release-sync` move from `devDependencies` to `dependencies`. `isolated-vm` was a devDependency during the spike and is not in this pull request.

Done, with these differences: the kit is prepared by `bun run kit` into a committed, generated `pipeline/prepared-kit.ts` (checked by a test) and not at build time, so a Vercel build needs no Bun transpiler; the WebAssembly and the worker thread are bundled by Turbopack and traced into the function (`next build` lists the `.wasm` among the route's files, and `next.config.ts` names it as well); the limits are set in `quickjs-core.ts` from the largest real sprite ("Limits"); the probes ran in the browser too, and the QuickJS rows of `probe-inprocess.ts` and the pixel identity of `measure-inprocess.ts --identity` still pass on the shared core (16 of 16 probes and 58 of 58 sprites under Bun and Node 24, after the limits changed).

### Not verified (in-process)

- Nothing ran in a Vercel Function: only macOS arm64 under Bun 1.4.3 and Node 24.19.0 (plus a first pass on Node 26.8.1), with the Node runs from a Bun-made bundle. Linux x86_64, Fluid compute, Next.js tracing of the `.wasm` and a function's memory ceiling were not tried.
- The probes attack the JavaScript surface. QuickJS and Emscripten themselves were not fuzzed, and no WebAssembly-level escape was attempted.
- The timings were taken on a loaded machine (load average 10-12), the Vercel Sandbox rows have 3 renders each, and the Vercel numbers are from a client in the UK.
- `isolated-vm`: the spike's crash on `memory-objects` (Node 24.19 and 26.8, with the kit loaded) was not reproduced in the bare re-run on Node 24.22.1 and 26.12.1, and the cause was not found; the kit-loaded setup was not repeated on the newer Node. The renderer is not in the tree, and a Linux prebuild on Vercel was not tried.
- Model-written sprites, as opposed to the 58 committed ones, were not rendered: a build that needs more stack or memory than the defaults would fail as a render error, not as a security problem.

## Direct execution in the browser (option E)

An experiment, not an adoption. The owner's question: download the creature's code to the client and run it with no sandbox, plain JavaScript in the browser, no QuickJS. **Adopting it would change the AGENTS.md hard rule (model code runs only in a sandbox, the allowlisted local renderer, or QuickJS with no host functions), which is the owner's call; this branch does not change the rule.** The QuickJS path stays the default; the direct path runs only with `?draw=direct` on the page. Measured on 24 Oct 2026 on the machine of "The code in the browser" (Mac, 10 cores, Bun 1.4.3, `next start`, Playwright 1.64.1: Chromium, and WebKit with the `iPhone 14 landscape` profile, which is Safari's engine on this Mac's CPU, not a phone). **The machine was shared and loaded (load average 7-14 on 10 cores) while these ran**: the two draw paths were interleaved sample by sample so the load hits both alike, but absolute numbers, and the frame-timing rows especially, are noisy. Everything is over loopback.

### What was built

- `src/scene/creature-direct-worker.ts`: a Web Worker that runs the prepared kit and the build as plain JavaScript, the way `pipeline/render/run_local.ts` does (`new Function(...kitNames, "POSE", build + "return build")`), and replies with the 128 x 128 RGBA pixels. `pipeline/build-script.ts` holds the part of `quickjs-core.ts` it shares (the kit as a script, the `export` strip, the seeded `Math.random`), so the worker carries no interpreter.
- `pipeline/build-direct-worker.ts` bundles that worker and the kit into one script, `public/creature-direct-worker.js` (git-ignored; `bun run dev` and `bun run build` make it). It is a file of its own so that its own HTTP response can carry a Content-Security-Policy, which is what limits a worker (below). 205,170 bytes raw, 55,772 sent.
- `src/scene/creature-render.ts`: `?draw=direct` selects it; a fresh worker per draw, terminated at a 2 s deadline; the reply's shape is checked on the page.
- `src/game/creature-signing.ts` and the `signature` field of a record's `build`: Ed25519 signing (below).
- `next.config.ts`: the policies (below), chosen at build time with `CREATURE_DIRECT_CSP`.
- `e2e/check-creature-direct.mjs` (`bun run check:creature-direct -- --url ... --keys FILE`) and `e2e/verify-visual.mjs --draw direct --keys FILE`.

### Containment

What a worker gives for free: no DOM, no page, no `window`, no cookies of its own, and no access to the page's variables; the page terminates it at the deadline, so a loop or a hang ends there. What the worker adds before any creature code runs: every name in its global scope that is not a language built-in is shadowed with `undefined` (on the scope and, where the engine allows, deleted from the prototypes it inherits from): `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `importScripts`, `indexedDB`, `caches`, `postMessage`, `Worker`, `SharedWorker`, `navigator`, timers, `Date`, `performance`, `crypto`, `console`, `WebAssembly`, 53 names are left, all of them the language's. The reply goes through a reference to `postMessage` taken before the strip, and the worker script is strict so that `caller` and `arguments` do not lead up to it. `Math.random` is seeded and there is no `Date`, as in #45, and the 20 hero frames and 18 sprites draw to the PNGs' bytes.

What this does not do, said plainly:
- **A constructor chain does not escape; it finds the stripped scope.** `(function(){}).constructor("return this")()`, `[].constructor.constructor(...)`, indirect `eval` and `Object.getPrototypeOf(globalThis)` all return the same global object the worker stripped (probe `escape-global`: same object on all four routes, no host name reachable). That is a property of stripping the one scope there is, and it is a blocklist's weakness too: it holds for the names it has seen. Anything a future browser adds to a worker's scope is shadowed (the strip enumerates the scope, it does not list names), but a new way into the network that is not a global name would not be.
- **`import()` is syntax, not a global, and cannot be shadowed.** With the scope stripped and no policy, `import("https://...")` was the one route left, in Chromium and WebKit: the canary server saw a request and the app's own API saw a `GET`. Only a policy closes it.
- **Memory is bounded by time only.** A build allocated 1 GiB of typed arrays and 10 million objects without being stopped, and 4 GiB in under the 2 s deadline in Chromium and WebKit; the page survived and the next draw was exact, but the browser gives a worker no memory limit and a longer deadline or a slower machine would let it go further. QuickJS stops the same probe at its 32 MiB cap.
- **CPU is bounded by the deadline.** The endless loop and the regular-expression bomb end at the 2 s terminate (WebKit ended the regex early); the page's timers and frames were not affected beyond the machine's noise.

### The Content-Security-Policy, measured

Four builds (`CREATURE_DIRECT_CSP` = `none`, `page`, `worker`, `both`) against the network probes. Each cell is requests that reached the canary server on another port / requests the app's API saw / storage written, summed over `net-cross-origin`, `net-same-origin`, `import-scripts-remote` and `storage`. "Plain" is the control: the same probes in an unstripped worker the page makes from a blob, which inherits the page's policy.

| Policy                                                                                                             | Direct worker, Chromium | Direct worker, WebKit | Plain worker, Chromium | Plain worker, WebKit |
| ------------------------------------------------------------------------------------------------------------------ | ----------------------- | --------------------- | ---------------------- | -------------------- |
| none                                                                                                               | 2 / 1 / 0               | 2 / 1 / 0             | 13 / 6 / 2             | 10 / 6 / 1           |
| page only (`connect-src 'self' blob: data:` among others, `?draw=direct` only)                                     | 2 / 1 / 0               | 2 / 1 / 0             | 0 / 6 / 2              | 0 / 6 / 1            |
| worker's own response only (`default-src 'none'; script-src 'unsafe-eval'; connect-src 'none'; worker-src 'none'`) | 0 / 0 / 0               | 0 / 0 / 0             | 13 / 6 / 0             | 10 / 6 / 0           |
| both (the default)                                                                                                 | 0 / 0 / 0               | 0 / 0 / 0             | 0 / 6 / 2              | 0 / 6 / 1            |

What it shows:
- **A page-level `connect-src 'self'` does not block the direct worker's cross-origin request.** A worker made from a URL takes its policy from its own response, not from the page; only a blob or data worker inherits the page's. The page policy did stop the plain blob worker's cross-origin requests (13 to 0), and left its same-origin API calls (6) and storage writes alone, as `'self'` says.
- **The policy that works is on the worker script's own response**, which is why the direct worker is a file of its own: `connect-src 'none'` stops `fetch`, XHR, WebSocket and EventSource, `script-src 'unsafe-eval'` (no source, so no URL) stops `importScripts` and `import()`, and `worker-src 'none'` stops nested workers. It needs `'unsafe-eval'` because the build is run with `new Function`. It held in Chromium and WebKit.
- **Effect on the rest of the app: none found.** The page policy (`default-src 'self'`, scripts `'self' 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval' blob:`, styles `'unsafe-inline'`, images `data: blob:`, fonts `data:`, `connect-src 'self' blob: data:`, `worker-src 'self' blob:`) is sent only for `/?draw=direct`. `'unsafe-inline'` is for Next's inline bootstrap, `'unsafe-eval'` for Pixi's shader compiler and `blob:` for Pixi's own workers, so it is a weak policy against script injection; its only job is the page's own `fetch`. The whole headed visual verifier ran on the direct path with it (`--draw direct`, 150 of 150 checks, in desktop Chromium and the WebKit iPhone profiles), the title page loaded with zero violations and page errors in both browsers, and the game drew through Pixi. The verifier's own run-to-run noise is up to 6.5% of a dawn frame (a second default pass changed `07-heir` 6.5%, `10-gamepad-dawn` 1.7% and `16-sea-dawn` 1.5% against the first; the direct pass changed `10-gamepad-dawn` 1.4% and `16-sea-dawn` 2.6%), and the creature's title, night, flash and hurt frames did not change between paths.
- **What a policy cannot do here:** it also needs to be kept. It is a header on one static file; a deployment that serves the file without it (a CDN rule, a rename) silently loses the network containment, and nothing in the page would notice. The Next `headers()` entry is the single place that sets it.

### Signing, and the supply-chain risk

**The risk.** With QuickJS, a tampered gallery record can at worst draw a wrong picture or burn a worker's time, because the code runs with nothing to reach. With direct execution, whoever can write the gallery (a leaked `BLOB_READ_WRITE_TOKEN`, a compromised deploy, a bug in the job that stores model output) can make **every player's browser run arbitrary JavaScript** the next time that creature is met. The worker's strip and the policy shrink what that code can reach; they are one browser-engine behaviour deep each, and the worker has the player's IP address and a CPU. This is the main reason to prefer a contained interpreter over a plain worker.

**What signing does about it.** When the job accepts a creature it signs the creature's id and both hashes (`lampwarden-creature-v1`, the id, the code hash and the pixel hash, newline-separated) with an Ed25519 private key from `CREATURE_SIGNING_KEY` (a Web Crypto key, PKCS#8 base64) and stores the signature in `build.signature`. The browser has the public key built into its bundle (`NEXT_PUBLIC_CREATURE_PUBLIC_KEY`, read at build time) and verifies the signature before it fetches the code, and the code's hash before it runs it; a creature that fails either is no creature that night. Writing the store is then not enough to make players run code: the attacker needs the private key, which lives only in the job's environment. Tried with a key generated for the experiment (kept in `/tmp`, never committed), a fresh browser context for each case, in both browsers:

| Record                                            | Result  | Code fetched | Direct worker started | Canary hits |
| ------------------------------------------------- | ------- | ------------ | --------------------- | ----------- |
| signed, code as signed                            | drawn   | yes          | yes                   | 0           |
| code replaced in the store, record untouched      | refused | yes          | no                    | 0           |
| code and record hashes replaced together (no key) | refused | no           | no                    | 0           |
| signed by another key                             | refused | no           | no                    | 0           |
| no signature                                      | refused | no           | no                    | 0           |

The replaced code in the last four cases fetched the canary URL; it never ran. `creature-signing.test.ts` and a job test cover the same at unit level.

**What signing does not address.** It authenticates the store, not the model. The server signs what the model wrote after the judge render accepted it, and a model (or a prompt injection in a brief) can write code that renders a good sprite in the server's QuickJS and does something else when it finds itself in a browser worker (the two engines differ in many observable ways). So a signed creature is still untrusted code, and the worker's containment and policy still have to hold; signing narrows who can put code in front of players from "anyone with store write access" to "the model and the job". It also adds a key to manage: rotating it means re-signing or dropping every earlier creature, and a key in the job's environment is a secret the job's compromise reveals. And the browser needs Ed25519 in Web Crypto (Chromium 137+, Safari 17+; both browsers here had it).

The direct server worker (the other lane's measurement of running the code in a Node worker on the server) is not repeated here; its numbers are not in this section.

### Recommendation

Do not adopt it as the default. It is 8 to 13 times faster than QuickJS and 5 times smaller on the wire, and with its strip and its policy it was contained against every probe tried, in two browsers. But its containment is two browser behaviours (a name strip that a future scope change or a syntax-level route can undo, and a response header on one file) where QuickJS's is that the code has nothing to name; it cannot bound memory at all; and the failure mode of a mistake is code execution on every player's machine, not a wrong picture. QuickJS is already fast enough for what the game does (a creature is drawn once, behind the title screen, in about a second); the thing direct execution buys that matters is animation, 20 frames in 2.7 s against 19 s, and option C buys that without running model code in the player's browser at all, at the price of shipping images. If the owner wants direct execution anyway: ship the signing with it (it works and refuses every tampered case here), keep `CREATURE_DIRECT_CSP=both` as a tested default, serve `creature-direct-worker.js` with the policy and a content hash in its name, check in CI that the header is on that response, and consider a rate limit on what a creature is allowed to cost (a 2 s deadline is already the cap on CPU).
